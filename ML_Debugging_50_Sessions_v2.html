§1 · Numerics & losses (1–5)

1numericsHand-rolled cross-entropy NaNs — but only for the EASY examples

Interviewer: "Custom CE with one-hot targets: -(onehot * log(probs)).sum(). Training is fine for an hour, then NaN — and the batches that trigger it are the ones the model gets RIGHT. v1 #7 was log(0) on the correct class; this is its mirror image."

def ce(probs, onehot):                  # probs from softmax: rows sum to 1
    return -(onehot * np.log(probs)).sum(1).mean()   # log of EVERY prob, incl. ~0 ones
# when the model is confident, wrong-class probs underflow to exactly 0.0
# onehot is 0 there, but 0 * log(0) = 0 * (-inf) = NaN — IEEE, not algebra
Bug · fix · theory
What to look for
  • NaN on confident/easy examples ⇒ a log or division touching probabilities the math says are 'multiplied by zero'. IEEE evaluates 0 · (−∞) to NaN — the mask does not save you if the −∞ is computed first.
  • The v1 #7 pattern (log of the correct class hitting 0) and this one bracket the same rule: never take a bare log of a softmax output — the failure just picks a different class to blow up on.
  • Grep-level tell: log(probs) anywhere. The fixed form indexes first, or better, never materializes probs at all.
def ce(logits, y):                      # y: integer labels
    logp = logits - logsumexp(logits, axis=1, keepdims=True)   # log-softmax, fused & stable
    return -logp[np.arange(len(y)), y].mean()                  # index FIRST, log never sees 0
Background. Two distinct log(0) routes hide in naive CE: v1 #7's log(p_correct) underflows when the model is wrong and confident; this one, $0\cdot\log(0)$ on off-classes, fires when it is right and confident — later in training, which is why it feels like the model "broke by getting good." The fused log-softmax ($z - \mathrm{logsumexp}(z)$) removes both: no probability is ever exponentiated and re-logged. Frameworks' cross_entropy takes logits for exactly this reason (#31's double-softmax is the same lesson from the other side).
2numericsbf16 training: loss becomes -inf on hard tokens only

Interviewer: "Same model, same data: fp32 run is clean; bf16 run occasionally logs loss = inf, traced to a few rare tokens. The loss code takes softmax, then log, in half precision. Explain why only HARD tokens die, and fix it without leaving bf16."

with autocast(dtype=torch.bfloat16):
    logits = model(x)                    # bf16: ~8 bits of mantissa
    p = logits.softmax(-1)               # a hard token's true prob ~1e-6 …
    loss = -p.gather(-1, y[:,None]).log().mean()   # …rounds to 0 in bf16 → log(0) = -inf
Bug · fix · theory
What to look for
  • Half-precision underflow is a THRESHOLD effect: easy tokens (p ≈ 0.9) survive the round-trip; rare/hard tokens (p ≈ 1e−6) round to 0 in low precision, and only they produce −inf. 'Only some examples NaN' + mixed precision ⇒ check the dynamic range of the intermediate.
  • softmax-then-log does exp → normalize → log: the exp/normalize round-trip is where the precision dies. log_softmax computes $z-\mathrm{logsumexp}(z)$ — subtraction in logit space, no tiny numbers ever stored.
  • Rule for mixed precision: losses and normalizations in fp32 — autocast frameworks do this for you until someone hand-rolls the loss.
with autocast(dtype=torch.bfloat16):
    logits = model(x)
loss = F.cross_entropy(logits.float(), y)   # log_softmax fused, computed in fp32
# (F.cross_entropy under autocast upcasts internally; the .float() makes it explicit)
Background. bf16 keeps fp32's exponent range but only ~3 decimal digits of mantissa; probabilities below ~1e-38 don't underflow, but the softmax NORMALIZATION quantizes small ratios to 0 long before that. The general statement of #7/v2-1/v2-2: the log of a computed probability is only as safe as the smallest probability you'll ever index — which for language models (rare tokens, 50k+ vocab) is guaranteed tiny. Keep everything in logit space; convert to probabilities only at the API boundary, in fp32.
3numericsKL distillation loss comes back NEGATIVE

Interviewer: "Distilling teacher→student with F.kl_div(student_probs, teacher_probs). The KL prints negative — which is mathematically impossible — and the student barely learns. Two API misuses, one line."

t_p = teacher_logits.softmax(-1)
s_p = student_logits.softmax(-1)
loss = F.kl_div(s_p, t_p)        # kl_div expects LOG-probs as input #1 — these are probs
# and default reduction='mean' averages over B*V elements, not over the batch
Bug · fix · theory
What to look for
  • A provably-nonnegative quantity printing negative ⇒ the API contract is violated, not the math. F.kl_div(input, target) wants input = log-probabilities; feed probs and you compute Σ t·(log t − p) — garbage that can be any sign.
  • Second trap: reduction='mean' divides by every ELEMENT (B·V), silently scaling the loss down by vocab size — gradients ~50k× too small, 'barely learns.' Use 'batchmean' (the docs themselves say so).
  • Sanity probe: KL(p‖p) must be exactly 0 — one line, catches both bugs.
t_p   = teacher_logits.softmax(-1)
s_logp = student_logits.log_softmax(-1)          # log-probs, stable
loss = F.kl_div(s_logp, t_p, reduction='batchmean')   # Σ t·(log t − log s) / B ≥ 0
Background. $\mathrm{KL}(t\|s)=\sum t(\log t-\log s)\ge 0$ with equality iff the distributions match — so a negative reading is a free, unambiguous bug alarm (use it: assert loss ≥ 0). The kl_div signature (input=log-probs, target=probs, batchmean) is the most-misused API in distillation code; the same contract confusion is #31's probs-into-CE wearing a different loss. Modern wrinkle: soft-target distillation at temperature τ needs the loss scaled by τ² to keep gradient magnitude comparable — forgetting it is the follow-up bug.
4gradientsGradient check fails everywhere — but the backprop is correct

Interviewer: "You finite-difference-check a hand-written MLP: every layer reports relative error ~1e-2, way over threshold. You've triple-checked the chain rule; it's right. The CHECKER is the bug. Two numerical sins in three lines."

def gradcheck(f, w, g_analytic, eps=1e-12):      # fp32 weights
    num = np.zeros_like(w)
    for i in range(w.size):
        w.flat[i] += eps                          # 1e-12 vanishes: w + eps == w in fp32
        num.flat[i] = (f(w) - f_base) / eps       # forward difference: O(eps) truncation
        w.flat[i] -= eps
    return abs(num - g_analytic).max()            # absolute error: wrong scale for big grads
Bug · fix · theory
What to look for
  • eps has a sweet spot, not a 'smaller is better' dial. Too small (1e−12 in fp32): w+eps==w, difference is pure rounding noise. Too big: truncation error. fp32 sweet spot ≈ 1e−3; fp64 ≈ 1e−6. If a gradcheck fails uniformly across all layers, suspect eps/dtype before the chain rule.
  • Forward difference $(f(w+\epsilon)-f(w))/\epsilon$ has $O(\epsilon)$ error; centered $(f(w+\epsilon)-f(w-\epsilon))/2\epsilon$ has $O(\epsilon^2)$ — always centered.
  • Compare with RELATIVE error $|a-n|/(|a|+|n|+\text{tiny})$ — an absolute threshold flags every large gradient and passes every dead one.
def gradcheck(f, w, g_analytic, eps=1e-6):       # and cast w to float64 first
    num = np.zeros_like(w)
    for i in range(w.size):
        old = w.flat[i]
        w.flat[i] = old + eps; fp = f(w)
        w.flat[i] = old - eps; fm = f(w)
        w.flat[i] = old
        num.flat[i] = (fp - fm) / (2 * eps)       # centered: O(eps^2)
    rel = abs(num - g_analytic) / (abs(num) + abs(g_analytic) + 1e-12)
    return rel.max()                               # pass: < 1e-5 in fp64
Background. Finite differences fight two error sources: truncation (Taylor remainder, shrinks with eps) and rounding (cancellation in $f(w+\epsilon)-f(w-\epsilon)$, GROWS as eps shrinks) — the optimum is $\epsilon\approx\sqrt[3]{\text{machine eps}}$ for centered differences, which is why fp64 + 1e-6 is the standard recipe. v1 #9 used the checker to convict the gradient; this session is the converse skill — knowing when the checker itself lies. Complete the pair and you can always answer 'how do you KNOW your backward is right?'
5gradientsGradient check passes per-layer, training still diverges — the check missed a tensor

Interviewer: "Hand-written 2-layer net: gradcheck (done right, fp64, centered) passes for W1, W2, b2… and training still explodes. Turns out one parameter was never checked, and its gradient has a bug that also explains the divergence. Read the code with checklist discipline."

def backward(x, y, cache):
    dz2 = cache.p - y                      # (B, C)  softmax-CE gradient: correct
    dW2 = cache.h.T @ dz2 / len(y)         # checked ✓
    db2 = dz2.mean(0)                      # checked ✓
    dh  = dz2 @ W2.T
    dz1 = dh * (cache.z1 > 0)              # ReLU mask: correct
    dW1 = x.T @ dz1 / len(y)               # checked ✓
    db1 = dz1.sum(0)                       # SUM, not mean — b1's gradient is B× too big
    return dW1, dW2, db2                   # …and b1 never returned: optimizer never sees it
# the gradcheck loop iterated over the RETURNED dict — b1 was invisible to it
Bug · fix · theory
What to look for
  • A gradient check only covers what it iterates over. Check completeness first: set(params) == set(grads). The most dangerous parameter is the one missing from the dict — it fails silently (v2's cousin of #40's unregistered modules).
  • Mixed sum/mean reductions across parameters = per-parameter learning-rate anarchy: b1 effectively trains at lr·B while everything else trains at lr. Divergence that 'gets worse with batch size' is this bug's signature.
  • Convention check is one glance: every gradient line should end with the SAME / len(y) or none — uniformity is the invariant, whichever convention you pick.
    dW1 = x.T @ dz1 / len(y)
    db1 = dz1.mean(0)                      # same reduction convention as every other grad
    return dW1, db1, dW2, db2              # every parameter accounted for
# and in the checker:
    assert set(grads) == set(params), 'unchecked parameter!'
Background. Loss-reduction convention (sum vs mean over the batch) must be applied uniformly: with mean-loss, every parameter's gradient carries 1/B; mixing conventions rescales one parameter's effective LR by B, which both diverges and — nastily — changes behavior when you retune batch size. The deeper habit this session drills: gradcheck is a COVERAGE tool, so its first assertion is completeness, then correctness. Frameworks make this failure shape reappear as: params filtered out of optimizer groups, requires_grad=False leftovers, and EMA shadows never updated.

6init30-layer ReLU MLP: activation norms halve every layer

Interviewer: "No normalization layers (it's a from-scratch exercise). Per-layer activation-norm printout: 12.1, 8.4, 5.9, 4.1 … ~0 by layer 20. Loss never moves. The init line is the whole bug — and the printout tells you the exact factor."

for l in range(L):
    W[l] = np.random.randn(d, d) * np.sqrt(1.0 / d)    # Xavier — designed for tanh
    # forward: h = relu(h @ W[l])
# ReLU zeroes half the variance: Var(out) = 0.5 * Var(in)  →  norms shrink ~1/√2 per layer
Bug · fix · theory
What to look for
  • Norms changing by a CONSTANT FACTOR per layer ⇒ init/gain mismatch — read the factor: ×0.7 ≈ 1/√2 is the ReLU half-variance signature; Xavier under ReLU exactly produces it.
  • He init (√(2/d)) exists to cancel ReLU's halving; Xavier (√(1/d)) balances tanh. Wrong pairing = geometric decay (or explosion) with no normalization to hide it.
  • This is v1 #10's disease measured with the same tool (norms-vs-layer plot); the variant to recognize instantly: gain mismatch vs #10's deeper-family causes. LayerNorm nets hide this at forward time — it resurfaces in the GRADIENTS.
    W[l] = np.random.randn(d, d) * np.sqrt(2.0 / d)    # He: the 2 cancels ReLU's 1/2
# check: per-layer activation norms now roughly constant
Background. For $h_{out} = \mathrm{relu}(W h_{in})$ with $W_{ij}\sim\mathcal N(0,\sigma^2)$: $\mathrm{Var}(Wh) = d\sigma^2\mathrm{Var}(h)$ and ReLU keeps half → $\mathrm{Var}(h_{out}) = \tfrac{d\sigma^2}{2}\mathrm{Var}(h)$. Criticality demands $d\sigma^2/2 = 1 \Rightarrow \sigma = \sqrt{2/d}$ (He). Depth turns any per-layer factor $c$ into $c^L$ — the same multiplicativity as #39's missing residual, expressed through init instead of wiring. The three defenses stack: correct gain (this), normalization (LN/BN), and residuals; modern transformers use all three, which is why this bug now mostly appears in from-scratch interview code.
7initFirst loss is 14.2, not ln(V) — and the model takes 5k steps to recover

Interviewer: "Tiny GPT, vocab 50k: expected first loss ln(50000) ≈ 10.8, observed 14.2. It does eventually train, but a reference run is miles ahead at equal steps. The init of ONE tensor explains both the 14.2 and the slow start. (Weight-tied head.)"

self.tok_emb = nn.Embedding(V, d)          # default init: N(0, 1) — std 1.0
self.head = nn.Linear(d, V, bias=False)
self.head.weight = self.tok_emb.weight     # tied: bad emb init hits TWICE
# logits = h @ emb.T: with std-1 embeddings and d=1024, logits ~ N(0, ~32²)
Bug · fix · theory
What to look for
  • First-loss arithmetic is a free diagnostic: uniform-random predictions give exactly ln V; a HIGHER first loss means the model starts confidently WRONG — logits already have large magnitude at init. Work backwards: big logits ← big embedding·hidden dot products ← std-1 init at d=1024 (√1024 ≈ 32).
  • Weight tying doubles the damage: oversized embeddings inflate the input activations AND the output logits. Softmax at logit-std ~30 is near one-hot → tiny gradients to everything but one class → the 5k-step 'recovery' is the model shrinking its own embeddings first.
  • GPT-2's magic 0.02: std chosen so logits start small (≈ flat softmax) — the model begins maximally uncertain, which is exactly where CE learns fastest.
nn.init.normal_(self.tok_emb.weight, std=0.02)   # logits start ~N(0, 0.02²·d) — near-flat softmax
self.head.weight = self.tok_emb.weight
# check: first loss ≈ ln V (10.82), first softmax ≈ uniform
Background. CE's gradient is $p - y$: when the softmax is saturated at the wrong class, $p-y$ is large but the SOFTMAX JACOBIAN is near-zero everywhere else, so learning stalls until logit scale shrinks — 'confidently wrong at init' is a tax paid in thousands of steps. First-loss ≈ ln V is therefore a cheap release gate for any classifier (v1 #6's flat-at-ln-C is the same number read the opposite way: there loss STAYS at ln V, here it STARTS above it). Interview extension: this is also why μP parameterization scales init with width — logit variance at init should be width-invariant.
8initPre-norm 48L: activations at layer 48 are 40× layer 1 — grad spikes at step 30k

Interviewer: "Pre-norm transformer, all residuals correct, LN everywhere — yet the residual-stream norm grows roughly linearly with depth, and late in training you get gradient spikes from the top layers. Nothing is 'wrong' line-by-line; something is missing that GPT-2 style inits have."

for block in blocks:                       # 48 of them
    x = x + block.attn(ln(x))              # each block ADDS a same-scale contribution
    x = x + block.mlp(ln(x))               # stream variance grows ~linearly with depth
# all Linear layers share one global init std — output projections included
Bug · fix · theory
What to look for
  • Pre-norm's cost: LN protects each block's INPUT, but the residual stream itself is never normalized — 2L same-scale additions grow its variance ~linearly (norm ~√(2L)). Late layers then operate at 40× scale: their gradients dominate, and spikes start there.
  • The standard fix is init-time, one line: scale each block's OUTPUT projection (attn out-proj, mlp down-proj) by 1/√(2L) — contributions shrink with depth, stream variance stays O(1). (GPT-2's 'scaled init'; μP and DeepNet are principled versions.)
  • Diagnostic that separates this from #39: here gradient norms are healthy-to-large toward the TOP and the model trains — the pathology is stability, not vanishing. Norm-vs-layer plots (v1 #10's tool) read the direction of trouble.
for name, p in model.named_parameters():
    if name.endswith(('attn.out_proj.weight', 'mlp.down_proj.weight')):
        nn.init.normal_(p, std=0.02 / math.sqrt(2 * L))   # residual-branch outputs: shrink by depth
# check: residual-stream RMS roughly flat across layers at init
Background. With $x_{l+1} = x_l + f_l(\mathrm{LN}(x_l))$ and independent same-variance branches, $\mathrm{Var}(x_L) \approx \mathrm{Var}(x_0) + \sum_l \mathrm{Var}(f_l) \propto L$: pre-norm buys trainability (identity path, near-identity init) at the price of an unnormalized, growing backbone. Scaling branch outputs by $1/\sqrt{2L}$ makes total added variance O(1) regardless of depth. This completes the depth triptych with #39 (no identity path → vanishing) and v2-6 (wrong gain → geometric decay): wiring, gain, and ACCUMULATION are three separate depth pathologies with three separate one-line fixes — name which one the symptom points to.

§3 · Train/eval & regularization (9–10)

9regularizationCustom dropout: accuracy drops when you turn it OFF

Interviewer: "From-scratch net with hand-rolled dropout. Counter-intuitive report: evaluating WITH dropout active scores better than the 'proper' eval with dropout disabled. That inversion is the fingerprint of one missing division. (v1 #12 was framework-mode misuse; this is the raw mechanism.)"

def dropout(x, p=0.5, training=True):
    if not training: return x               # eval: pass through — sounds right…
    return x * (np.random.rand(*x.shape) > p)    # train: mask only, NO 1/(1-p) rescale
# train-time E[output] = (1-p)·x  ;  eval-time output = x  →  eval activations 2× larger
Bug · fix · theory
What to look for
  • 'Better WITH dropout at eval' inverts the usual #12 symptom and pins the bug precisely: the network calibrated itself to train-time magnitudes ((1−p)·x); proper eval feeds it 2× that — every downstream layer sees out-of-distribution scale. Keeping dropout on 'fixes' eval by keeping the broken scale.
  • Inverted dropout divides by (1−p) AT TRAIN TIME so eval is a clean identity — that's why frameworks implement it this way (and why model.eval() alone is enough for them).
  • Cheap probe: print mean activation norm train-mode vs eval-mode on the SAME batch — they must match. Any train/eval scale gap = un-inverted dropout somewhere.
def dropout(x, p=0.5, training=True):
    if not training: return x
    mask = np.random.rand(*x.shape) > p
    return x * mask / (1 - p)               # inverted dropout: E[output] = x in BOTH modes
Background. Dropout's contract is $\mathbb E[\text{out}] = x$ so the surrounding network is scale-stationary across modes; the original 2012 formulation rescaled by (1−p) at TEST time instead, and 'inverted' dropout moved the correction to training so inference is untouched — mixing the two conventions (rescaling in neither place, or both) is the classic from-scratch bug. General principle worth saying: any stochastic train-time regularizer must preserve some moment the network depends on (dropout: mean; BatchNorm: running stats standing in for batch stats) — v1 #12/#13 and this session are one family: train/eval asymmetry with a broken invariant.

Background. Dropout inflates measured train loss (the network is literally noisier when scored), and epoch-averaging mixes early-bad with late-good — together they routinely produce val 5-15% below train with zero leakage, which is why 'val < train' alone proves nothing in either direction. The discipline is a controlled comparison (same weights, same mode, same time), after which any remaining gap IS evidence — usually of overlap, the #35-family disease. # reward-to-go must be r_t + r_{t+1} + … : the FUTURE, not the past
# (and gamma silently ignored)
Bug · fix · theory
What to look for
  • Credit must be causal: an action can only be credited with rewards AFTER it. Forward cumsum gives each step the PAST — early actions get weighted by almost nothing, late actions by the whole episode's history they didn't cause. 'Great openings, aimless endgame' is exactly inverted credit.
  • Correct one-liners: reversed cumsum cumsum(r[::-1])[::-1], or the backward recursion G[t] = r[t] + γ·G[t+1] — the same reversed-iteration pattern GAE needs (#47): all return-like quantities are computed BACK-to-front.
  • γ dropped is the second bug: undiscounted returns on long episodes = high variance + no horizon. Check: G[T-1] must equal r[T-1] exactly — a one-assert test.
def returns(r, gamma=0.99):
    G = np.zeros_like(r); acc = 0.0
    for t in reversed(range(len(r))):      # future → past, like GAE (#47)
        acc = r[t] + gamma * acc
        G[t] = acc
    return G                               # G[t] = Σ_{t'≥t} γ^{t'-t} r_{t'}
Background. The policy-gradient weight for action $a_t$ must be (an estimate of) $Q(s_t,a_t)$ — the expected FUTURE return — because $\nabla\log\pi(a_t)$ scaled by past rewards has zero expectation but pure variance (past rewards are constants w.r.t. $a_t$; this is the same 'action-independent terms cancel' logic as baselines, Q58). cumsum-vs-reversed-cumsum is the cleanest single-line embodiment of RL's credit-assignment direction, and it foreshadows every recursion in the family: reward-to-go, GAE's $\delta$ recursion (#47), and TD(λ) all iterate from the end of time backwards. If an RL loop contains a FORWARD loop over time producing a return-like array, it's guilty until proven innocent.

    q = rope(x_t @ W.q, pos=pos)

    return attend(q, cache), cache
Background. What to look for
  • Nonnegativity of KL is a property of the EXPECTATION, not of samples. The single-sample estimator k1 = log π − log ref is unbiased BECAUSE its negative excursions cancel its positive ones; clamping deletes the negative half → a biased meter whose error grows exactly as the policy concentrates on tokens ref dislikes. The control loop (β against measured KL, or adaptive-β) is now regulating a fiction.
  • Meters that are also OBJECTIVES corrupt doubly: the clamped penalty stops penalizing the specific drift pattern 'high π, low ref, occasionally ref-favored tokens' — a canyon for the optimizer to hide divergence in.
  • The known-good tool: the k3 estimator (r − 1 − log r, r = ref/π ratio) — nonnegative BY CONSTRUCTION and still unbiased-in-the-limit-useful; this is what mainstream RLHF stacks use precisely so nobody is tempted to clamp. If your per-token KL never prints negative and you didn't choose k3 on purpose, someone clamped.
ratio = (logp_ref - logp_policy).exp()         # r = ref/π per token
kl_t = ratio - 1 - (logp_ref - logp_policy)    # k3: ≥ 0 pointwise AND low-bias (Schulman)
