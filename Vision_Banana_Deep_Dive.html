§1 · What Vision Banana is

The claim: a production-grade image generator is already a generalist perception model — it just doesn't know how to answer in the formats vision benchmarks expect. Vision Banana applies "lightweight instruction tuning" to Nano Banana Pro (NBP), mixing a very low ratio of vision-task data into NBP's original training mixture. No new architecture, no task heads, no auxiliary losses, no specialized decoders. One set of weights then handles:

  • Semantic segmentation (open-vocabulary, color mapping specified in the prompt)
  • Instance segmentation (model invents a distinct color per instance)
  • Referring-expression & reasoning segmentation (RefCOCOg, ReasonSeg)
  • Monocular metric depth — absolute meters, no camera intrinsics at train or test time
  • Surface normal estimation
  • …while retaining text-to-image generation and editing at roughly base-model quality.
Key idea Every task output is parameterized as an RGB image, so every task becomes conditional image generation: "here is an image + an instruction, generate the answer-image." Perception is reframed as a species of image editing — exactly what the base model was already trained to do.

There are four broad strategies for unifying vision tasks. Vision Banana bets on the last:

What's genuinely new versus Painter/Marigold-era work: (1) the base is a frontier-scale proprietary generator, not SD-2/small ViTs; (2) one checkpoint covers 2D + 3D + generation simultaneously (Marigold/Lotus are per-task finetunes); (3) the task interface is natural language — color mappings, colormap choices, target classes all specified in the prompt, giving open vocabulary for free; (4) depth is metric, not affine-invariant — no ground-truth alignment at eval.

The whole system: model weights are task-agnostic; all task specificity lives in the prompt (input side) and a deterministic decoder (output side).

§3 · Task encodings & decoders — the technical meat

3.1 Semantic segmentation — colors as class logits

The prompt specifies the class→color mapping directly: "Generate a semantic segmentation visualization, using this color mapping: {sky: (70,130,180), road: (128,64,128), …}" — as natural language, JSON, hex codes, or RGB tuples. Because classes are named per-prompt, the vocabulary is open: any noun phrase can be a class.

Decoding: each generated pixel $\hat{p} \in [0,255]^3$ is assigned to class $k^* = \arg\min_k \lVert \hat{p} - c_k \rVert_2$ (nearest target color in RGB Euclidean distance). This is soft: the generator never emits exact colors (VAE compression, anti-aliasing), but as long as its color error is smaller than half the inter-class color distance, decoding is exact — choosing well-separated colors in the prompt is part of the method.

3.2 Instance segmentation — the model invents the palette

Here the number of instances is unknown a priori, so the prompt just says "color each <class> instance differently." The model chooses arbitrary distinct colors; the decoder (paper Appendix A) recovers instances with a multi-stage connected-component pipeline:

  1. Background init: pixels within color tolerance $\tau = 14$ of the declared background color are removed.
  2. Seeded floodfill with 16-connectivity and color-similarity threshold $\tau^2$ grows instance components.
  3. Noise pruning: components $< 0.02\%$ of image area are discarded (anti-aliasing slivers).
  4. Boundary cleanup: $3{\times}3$ binary erosion with threshold $\theta_{\text{erosion}} = 0.1$ kills edge artifacts.
  5. Fragment merging: components with similar color whose bounding boxes (expanded by factor $\gamma = 5.0$) overlap are merged — handles instances split by occlusion.
Interview angle This decoder is where the elegance leaks: the "no task-specific components" story is true of the weights, but a nontrivial hand-tuned decoder sits on the output. A sharp interviewer will push here — own it: the decoder is deterministic post-processing, cheap, and task-generic in spirit (color → set structure), but instance identity via color is fragile when the model picks two near-identical colors (see Q&A 4).

3.3 Metric depth — an invertible false-color code for $[0,\infty)$

Depth is unbounded; RGB is a bounded cube. The encoding is two-stage:

Stage 1 — squash depth to $[0,1]$ with the power transform (Barron 2025), $\lambda = -3$, $c = 10/3$:

$$ t = f(d; \lambda, c) = 1 - \Big(1 - \frac{d}{\lambda c}\Big)^{\lambda + 1} \;\;\xrightarrow{\;\lambda=-3,\; c=10/3\;}\;\; t = 1 - \Big(1 + \frac{d}{10}\Big)^{-2} $$

Strictly monotone, $t(0)=0$, $t(\infty)=1$, with closed-form inverse $d = 10\big((1-t)^{-1/2} - 1\big)$. The resolution allocation is the design decision: $dt/dd = 0.2\,(1+d/10)^{-3}$, so color-space resolution is spent densely on near depth — half the entire code range covers $d < 10(\sqrt{2}-1) \approx 4.1\,$m. That matches how metric-depth metrics (δ₁, AbsRel) price relative error.

Stage 2 — route $t$ along a piecewise-linear path through the RGB cube, visiting the corners black→red→yellow→green→cyan→blue→violet→white (a rainbow, Hilbert-curve-like path). Compared to grayscale (256 levels), a 7-edge path gives $\approx 7 \times 255 \approx 1785$ distinguishable levels — about 2.8 extra bits of depth precision — and false-color "scientific visualization" imagery is squarely in-distribution for a web-trained generator. Training also augments with Plasma / Inferno / Viridis / grayscale colormaps (prompt-selectable) so the model learns the concept "encode depth in a stated colormap" rather than memorizing one palette.

Decoding: project each generated pixel onto the nearest point of the path (nearest line segment), read off $\hat{t}$ from the arc-length position, invert the power transform → meters. Strictly invertible by construction. With intrinsics available at test time, the metric depth map back-projects to a 3D point cloud.

3.4 Surface normals — direct linear code

The camera-space unit normal $\mathbf{n} = (x, y, z) \in [-1,1]^3$ maps linearly to channels (values clamped to $[0,1]$, then $\times 255$):

$$ R = \frac{1 - x}{2}, \qquad G = \frac{1 + y}{2}, \qquad B = \frac{1 + z}{2} $$

— the standard "normal map" false-color convention (the sign flip on $x$ is a camera-handedness choice; all that matters is that encode and decode agree). Decoding inverts the affine map and re-normalizes to unit length, which projects out most per-channel generation noise.

3.5 Referring / reasoning segmentation

Free-form language picks the target: "segment the cat that is stretching in cyan", "the object used as a game controller in #10aa05". Notably these compositions were not explicitly trained — referring-style prompts transfer onto the segmentation format, an emergent cross-task combination. On ReasonSeg, a reasoning MLLM (Gemini 2.5 Pro) first resolves what to segment, then Vision Banana executes — so that number is a pipeline result, not a single-model result.

§6 · Why does generation pretraining give perception?

The mechanism argument, in interview-speakable form:

  • Generation strictly requires implicit perception. To render a scene with consistent occlusion, shadows, contact points, and object scale, the model must internally represent segmentation-like grouping, depth ordering, and surface orientation. Perception tasks just read out what generation had to compute anyway.
  • The evidence chain got stronger over time: DIFT correspondence from diffusion features (2023) → Marigold: 74k synthetic pairs turn SD-2 into a zero-shot SOTA relative depth model (2024) → Lotus, DICEPTION → Vision Banana: frontier scale, metric depth, multi-task, single checkpoint, generation retained (2026). Each step raises the claim from "generative features help" to "the generator is the vision model."
  • Metric scale without intrinsics is the most striking readout: absolute meters require priors over object sizes, ground planes, and the photographer-camera joint distribution — priors only a web-scale generative model plausibly has (see Q&A 5).
  • The confound to keep in your pocket: NBP's pretraining mixture is undisclosed. If it already included interleaved understanding data or an MLLM backbone (likely, Gemini lineage), then "pure image-generation pretraining suffices" is not exactly what was shown — what was shown is "a frontier generator checkpoint contains generalist perception, extractable with light tuning." Saying this unprompted is a research-taste flex.

§7 · Ties to your story

  • MMU⇄MMGen transfer doc: Vision Banana is the new strongest entry for the Gen→MMU dense-output channel — Marigold's argument upgraded to frontier scale, metric, and multi-task. It does not resolve objective-level synergy (no FLOP-matched specialist baseline), which keeps your "the missing experiment" punchline intact.
  • LatentFusion contrast (your proposal): Vision Banana unifies in pixel space (interpretable, precision-capped at 8 bits × VAE, pays full generation cost per prediction); LatentFusion predicts in frozen SSL latent space (cheap, information-dense, but needs decoders to read out). They are the two poles of the same design axis — being fluent in both sides of that trade is a great "what would you do next" bridge.
  • Scaling-law angle: if generative pretraining is vision's pretraining substrate, the follow-up question is what is the scaling law of emergent perception — perception readout quality vs generator compute, and whether the tuning-data requirement shrinks with scale (cf. your Q103 image-gen scaling-law entry). Nobody has published this curve; proposing it is a free research-idea answer.

§8 · Deep technical Q&A

Click to reveal. Ordered roughly encode → decode → training → analysis → design.

1 · Why parameterize task outputs as RGB images instead of adding task heads or output tokens? Full trade-off. ▶

For: (1) zero architecture change — the entire generative prior, including the decoder's learned ability to draw sharp boundaries, is reused; (2) tasks become in-distribution image editing, so a lightly-tuned model generalizes (open vocabulary, novel compositions) instead of learning a head from scratch; (3) one interface for all dense tasks ⇒ a single checkpoint, and new tasks are added with prompts + data, not surgery; (4) human-inspectable outputs.

Against: (1) precision ceiling — 8-bit RGB through a lossy VAE bounds regression accuracy (mitigated by the colormap-path trick, Q12); (2) no logits ⇒ no native confidence/calibration (Q10); (3) inference cost is a full image generation per prediction vs one forward pass for a specialist (Q13); (4) a hand-tuned decoder reappears outside the network (§3.2); (5) sparse/structured outputs (boxes, keypoints) waste the interface (Q11).

One-liner: "RGB output trades precision and compute for maximal reuse of the generative prior — the right trade exactly when the prior is frontier-scale."

2 · Design the depth→[0,1] squash. Why the power transform with λ = −3, c = 10/3, and not linear or log? ▶

Requirements: bijective on $[0,\infty) \to [0,1)$, closed-form inverse, and resolution allocated to match how depth error is priced ($\delta_1$, AbsRel are relative metrics ⇒ want roughly constant relative resolution).

Linear $t = d/d_{max}$: needs a hard $d_{max}$, wastes most of the range on the far field where relative precision matters least. Log $t \propto \log d$: unbounded at both ends, needs two clips. Inverse/disparity $t = 1/(1+d)$: workable, but fixed decay shape. The power transform $f(d;\lambda,c) = 1 - (1 - \frac{d}{\lambda c})^{\lambda+1}$ is a tunable family interpolating between these; with $\lambda=-3, c=10/3$:

$$ t = 1 - (1 + d/10)^{-2}, \qquad d = 10\big((1-t)^{-1/2} - 1\big), \qquad \frac{dt}{dd} = \frac{0.2}{(1+d/10)^{3}} $$

Half the code range covers $d \le 10(\sqrt2 - 1) \approx 4.1$ m; the tail decays polynomially so 20–80 m still gets usable resolution (log would over-compress, linear would over-spend). The constants set the "knee" at ~10 m — a prior about where photos live.

3 · Why route t along a rainbow path through the RGB cube instead of just outputting grayscale? ▶

(1) Precision: grayscale = 256 levels (8 bits). A piecewise-linear path through 7 edges of the cube ≈ $7 \times 255 \approx 1785$ levels ≈ 10.8 bits — 2.8 extra bits of depth resolution from the same pixels. (2) In-distribution outputs: web pretraining is full of false-color scientific visualizations; "render a rainbow depth map" is a style the generator already knows, whereas precise smooth grayscale ramps are exactly what VAEs banding-artifact. (3) Noise robustness: decoding projects a 3-vector onto a 1-D path — per-channel generation noise orthogonal to the path is discarded. (4) Colormap augmentation (Plasma/Inferno/Viridis/gray, selected by prompt) forces the model to bind the concept depth-to-stated-code rather than memorize a palette — the same reason instruction diversity matters in LLM tuning.

4 · Instance segmentation: the model picks arbitrary colors. Walk through the decoder and its failure modes. ▶

Pipeline (Appendix A): background removal by color tolerance $\tau{=}14$ → seeded floodfill, 16-connectivity, similarity threshold $\tau^2$ → prune components $<0.02\%$ of area → $3{\times}3$ binary erosion ($\theta{=}0.1$) for boundary anti-aliasing artifacts → merge same-color fragments whose bboxes, expanded $\gamma{=}5\times$, overlap (occlusion-split instances).

Failure modes: (a) two instances assigned near-identical colors collapse into one — color assignment is uncontrolled model behavior; (b) anti-aliased boundary pixels form sliver components (handled by pruning+erosion, at the cost of slightly shrunken masks — the paper notes masks run "slightly smaller and finer" than GT); (c) the $\gamma$ merge can fuse genuinely distinct same-colored far-apart instances; (d) VAE color drift eats into the $\tau$ budget. Design fix you can offer: constrain the palette in the prompt (e.g., maximally-separated colors from a fixed list, ordered left-to-right) — converts an open assignment problem into a decodable code.

5 · Metric depth with no camera intrinsics at train or test time — how is that even possible, and when does it break? ▶

Monocular metric depth is formally ill-posed without focal length: scaling the scene by $s$ and the focal length by $s$ leaves the projection invariant. The model must therefore infer implicit intrinsics + scale jointly from content: known object sizes (people, cars, doors), ground-plane/horizon geometry, perspective-gradient statistics, and the strong empirical prior that web photos come from a narrow distribution of (camera, scene) pairs. It's a Bayesian answer: $p(d \mid \text{image})$ concentrates because $p(\text{camera}, \text{scene})$ does.

Breaks when the prior breaks: telephoto compression and macro shots (focal length far from modal), scale-free content (rocks, clouds, textures), miniatures/tilt-shift (deliberately adversarial to the prior), fisheye. The kicker: tuning used synthetic renders only — so the real-world scale prior must come from generative pretraining, not the depth data. That's the single strongest piece of evidence for the paper's thesis.

6 · "Light tuning at a very low mixture ratio suffices" — what does that imply scientifically, and how would you test it? ▶

Implication: the capability pre-exists in the generator; tuning performs format alignment — the superficial-alignment hypothesis (LIMA) transported to vision. Supporting signals: SOTA with pseudo/synthetic labels only; emergent untrained compositions (referring × instance); generation quality retained (the weights barely moved).

Tests I'd run: (1) zero-shot the base NBP with the same prompts — any partial capability before tuning? (2) tuning-set-size scaling curve — format-learning predicts fast saturation (Marigold's 74k-sample result is the precedent); (3) linear-probe intermediate features for depth/segmentation pre-tuning — if probes are strong, tuning is readout; (4) freeze-most tuning (LoRA rank sweep) — format alignment should survive tiny trainable subspaces.

7 · How do you add perception without destroying generation? Why does the low mixture ratio work? ▶

It's replay: vision data is mixed into the original training mixture, so the gradient distribution stays near pretraining and catastrophic forgetting is suppressed — same recipe as LLM continued-pretraining. The low ratio works because format-teaching is gradient-cheap: the tasks reuse existing features, so few, consistent gradients suffice; a high ratio would push the model toward flat-color "visualization style" outputs globally (style drift). Receipts: GenAI-Bench T2I win-rate 53.5% vs its own base (slightly improved — plausibly the dense spatial supervision sharpens layout), ImgEdit 47.8% (slight cost). Measuring retention by side-by-side win rate rather than FID is itself a point worth making: it detects distribution-level drift that FID smooths over.

9 · Why did instance segmentation on SA-Co need a Gemini MLLM as a negative-query filter? What's the deeper issue? ▶

SA-Co's cgF1 (classification-gated F1) scores you on negative queries too — asked for a class that isn't present, you must output nothing. A generative decoder has no natural "abstain" in pixel space: it must emit an image, it was tuned mostly on positives, so it hallucinates plausible masks for absent objects. The fix is a pre-filter: an MLLM answers "is X present?" and gates generation.

Deeper issue: the RGB interface lacks a null token and lacks calibrated confidence — rejection, OOD, and abstention all have to be bolted on outside the model. This is the genuine open edge of output-space unification (contrast: a token-based unifier can emit an "empty" token and expose logprobs).

10 · The output is an RGB image — where do you get uncertainty? ▶

(1) Sampling ensembles: generate $K$ answer-images with different noise seeds; per-pixel class agreement rate (seg) or depth variance = epistemic uncertainty. Principled, costs $K\times$ generation. (2) Decode-distance proxy: distance from the emitted pixel to the nearest legal code (class color / colormap path) — off-manifold pixels signal model confusion; cheap but conflates noise with uncertainty. (3) AR logprobs if the generator is autoregressive — token entropy maps back to spatial regions. (4) Distill into a specialist head with real logits when deployment needs calibration. In an interview, lead with (1) and note the compute trade — it mirrors self-consistency in LLMs.

11 · Extend the RGB parameterization to optical flow, boxes, keypoints, video tracking. Design encodings and name the pitfalls. ▶

Optical flow: the Middlebury color wheel (hue = direction, saturation = magnitude) is already a near-invertible 2D code; make it exact by fixing the magnitude normalization in the prompt or reusing the depth power-transform on $\lVert v \rVert$. Natural fit — flow is dense and image-shaped.

Boxes: draw filled per-instance-color rectangles, decode extremal coordinates — but overlapping boxes occlude each other; corner-dot encodings decode ambiguously. Sparse structured outputs are better emitted as text tokens by an MLLM; forcing them into pixels wastes the interface. Keypoints: per-joint color disks, decode blob centroids — works, but sub-pixel precision is capped and occluded-joint conventions get awkward. Video tracking: requires the same instance to keep the same color across independently generated frames — a temporal-consistency constraint the generator doesn't natively guarantee; you'd condition each frame on the previous answer-frame (autoregressive in time) and accept drift.

Rule to state: the interface excels exactly when the output is a dense field over pixels; the sparser and more structured the output, the more you should hand it to tokens.

12 · Compute the effective depth precision of the encoding. Is 8-bit RGB the accuracy bottleneck? ▶

Path resolution: $\Delta t \approx 1/1785 \approx 5.6\times10^{-4}$. Quantization error in meters: $\Delta d = \Delta t \,/\, \frac{dt}{dd} = \Delta t \cdot 5\,(1+d/10)^3$:

  • $d = 2$ m: $\Delta d \approx 4.8$ mm (0.24%)
  • $d = 10$ m: $\Delta d \approx 2.2$ cm (0.22%)
  • $d = 50$ m: $\Delta d \approx 0.60$ m (1.2%)

So the code carries ~0.2–1% relative error — while the model's achieved AbsRel is ~8%. Conclusion: quantization is not the bottleneck; generation fidelity is (VAE reconstruction, sampling noise, boundary sharpness). This is the calculation that shows you actually understand the encoding — the colormap has ~30× more precision headroom than the model uses.

13 · Vision Banana vs SAM 3 in production — cost model and deployment decision. ▶

Cost: one prediction = a full frontier-model image generation (multi-step sampling or a long AR decode over image tokens) + decoding + possibly an MLLM filter call — orders of magnitude more FLOPs and latency than a single SAM/DAv3 forward pass. The paper concedes "significantly higher" compute and reports no latency.

Deploy the specialist when: latency/edge constraints, closed vocabulary, high QPS. Deploy Vision Banana when: open-vocabulary or language-specified tasks, long-tail concepts, tasks with no trained specialist, low-volume/high-value queries, rapid prototyping. The pattern that actually ships: generalist-as-teacher — use Vision Banana as a pseudo-label factory to mint training data and distill small specialists per deployment (the same relationship frontier LLMs have to production classifiers).

14 · What does this paper actually settle in the generation⇄understanding unification debate — and what does it not? ▶

Settles (strengthens): the Gen→MMU dense-output channel — a T2I prior contains extractable geometry and semantics, now demonstrated at frontier scale, metric, multi-task, with generation retained. Marigold's argument, upgraded.

Does not settle: (1) objective-level synergy in shared weights — there's no FLOP-matched comparison against a specialist trained with generator-scale compute, so "generalist wins per FLOP" is unproven (intercept win, not slope win); (2) purity of the claim — NBP's pretraining mixture is undisclosed and likely includes understanding-flavored data via its Gemini lineage, so this shows "a frontier generator checkpoint contains perception," not "pixels-only generative pretraining suffices." Raising both caveats unprompted, then saying the missing experiment is the FLOP-matched 4-arm grid, is the research-taste answer.

15 · You're the reviewer: design the ablations the paper owes you. ▶
  1. Base-model probe: zero/few-shot the untuned NBP with identical prompts — quantifies how much capability tuning "unlocked" vs "revealed."
  2. Tuning-data scaling curve: performance vs vision-sample count; format-alignment predicts early saturation.
  3. Mixture-ratio sweep: the perception-gain vs generation-retention Pareto frontier — where does forgetting start?
  4. Colormap ablation: grayscale vs rainbow-path vs single-fixed vs augmented-set — isolates how much the encoding (vs the prior) contributes.
  5. FLOP-matched specialist: same total compute into a dedicated depth/seg model — the per-FLOP claim.
  6. Decoder sensitivity: mIoU as a function of τ, erosion, γ — how much of the score lives in post-processing?
  7. Pretraining-attribution: ablate visualization-style imagery (charts, false-color maps) from pretraining — does the depth readout still tune in fast? Tests where the readout format prior comes from.
