The debugging protocol (say this out loud)

Debugging rounds grade the search process, not the epiphany. The interviewer wants to see a binary search over hypotheses, each killed by cheap evidence. The order that works:

  1. Restate the symptom precisely. "Loss is flat at 2.30 from step 0" is a different disease than "loss decreases then NaNs at step 4k." Ask for the exact numbers — they're often the answer (2.30 ≈ $\ln 10$).
  2. Data before model. Print one batch. Check shapes, dtypes, label range, X↔y alignment, a decoded example. Half of real bugs die here.
  3. Shapes and axes next. Annotate every tensor line with its shape. Hunt for silent broadcasting (a (n,1) meeting a (n,)), reductions without axis=/keepdims=, and softmax/norm over the wrong axis.
  4. Numerics. Anything with a bare exp, log, sqrt, or division is a NaN factory. Check what happens at the extreme input.
  5. State over time. Bugs that need iterations to show: gradients not zeroed, stale caches, mutable default args, schedulers stepped at the wrong cadence, EMA/running stats.
  6. Train/eval asymmetry. Anything that behaves differently between modes — dropout, BatchNorm, masking, sampling — is a prime suspect when train looks good and eval doesn't.
  7. Verify the fix with the symptom. Re-run the exact thing that was broken, and say what you expect to see before you run it.
The one-liner interviewers remember "Let me localize before I theorize" — reproduce, then bisect: half the pipeline at a time (data → forward → loss → backward → update), asserting one invariant at each cut (shapes, finiteness, rows-sum-to-1, gradient sign, param norms actually changing).

6losses"Here is the loss curve — why?" (stuck at 2.303)

Interviewer: "MNIST classifier, 10 classes. Here's the training loss. It never moves. The data loader is verified. Tell me what the number 2.303 is telling you, then find the bug."

Loss pinned at ln(10) ≈ 2.303 from step 0 — the model is exactly as good as guessing uniformly over 10 classes.
def forward(X, W, b):                    # X: (B, 784), W: (784, 10)
    logits = X @ W + b                   # (B, 10)
    z = logits - logits.max(axis=0, keepdims=True)   # axis=0: normalizing over the BATCH
    e = np.exp(z)
    probs = e / e.sum(axis=0, keepdims=True)          # each CLASS column sums to 1 across examples
    return probs
Bug · fix · theory
What to look for
  • Decode the constant first. $\ln 10 = 2.303$, $\ln 2 = 0.693$, $\ln 100 = 4.605$, $\ln 32000 \approx 10.4$, $\ln 50257 \approx 10.8$. A loss pinned at $\ln C$ means the model outputs the uniform distribution (or the gradient never reaches the weights). Knowing these constants cold is the single highest-value debugging habit.
  • Softmax over the batch axis still produces a valid-looking probability tensor — shapes don't change, nothing crashes. The invariant that catches it: probs.sum(axis=-1) must be all-ones per example. Assert it.
  • Why it trains to uniform rather than diverging: with batch-axis softmax the per-example distribution is unconstrained noise, the gradient averages out, and CE against it settles at chance level.
def forward(X, W, b):
    logits = X @ W + b
    z = logits - logits.max(axis=-1, keepdims=True)   # per-example over CLASSES
    e = np.exp(z)
    probs = e / e.sum(axis=-1, keepdims=True)
    assert np.allclose(probs.sum(axis=-1), 1.0)       # the invariant, stated out loud
    return probs
Background. Cross-entropy at the uniform distribution equals $\log C$ exactly, and it is also the loss of a freshly-initialized model with small logits — so "starts at 2.30" is healthy for MNIST, but "stays at 2.30" means zero learning signal is reaching the logits. The differential diagnosis for a $\ln C$ plateau, in order of frequency: softmax/CE over the wrong axis, features↔labels desynchronized by shuffling (#18), parameters not in the optimizer (#40), LR = 0 or gradients zeroed after computation. All four produce byte-identical loss curves — the fastest discriminator is to overfit a single batch of 8 examples: a healthy pipeline drives loss to ~0 in a hundred steps, and whichever stage prevents that is your bug.
7lossesCross-entropy NaNs once the model gets good

Interviewer: "Language-model pretraining loss: smooth for 4k steps, then NaN. No divergence before it — loss was still going down. Rule out the optimizer; the bug is in this loss function."

Loss decreasing smoothly, then NaN with no preceding spike — numerical bug reached by confidence, not instability.
def ce_loss(logits, targets):            # logits: (B, V), targets: (B,) int
    z = logits - logits.max(axis=-1, keepdims=True)
    e = np.exp(z)
    probs = e / e.sum(axis=-1, keepdims=True)         # stable softmax — fine so far
    return -np.mean(np.log(probs[np.arange(len(targets)), targets]))  # log of a computed prob
Bug · fix · theory
What to look for
  • Two-step log(softmax(x)) is always the suspect when CE NaNs late in training. The softmax itself is stable, but a non-target class the model has learned to rule out gets probability that underflows to exactly 0.0; if that class is ever the target (label noise! it happens), log(0) = −inf, and the mean is NaN.
  • "NaN reached by success" (loss still decreasing) vs "NaN reached by instability" (spike first) is the key discrimination — it tells you to look in the loss's extreme-confidence path, not at the optimizer.
  • The fix is one identity: $\log p_t = z_t - \log\sum_j e^{z_j}$ — compute log-softmax directly, never materialize the probability.
def ce_loss(logits, targets):
    z = logits - logits.max(axis=-1, keepdims=True)
    logZ = np.log(np.exp(z).sum(axis=-1, keepdims=True))   # log-sum-exp, safe: z ≤ 0
    logp = z - logZ                                         # log-softmax in one pass
    return -np.mean(logp[np.arange(len(targets)), targets])
Background. After the max-subtraction, every $z_j \le 0$, so $e^{z_j} \in (0,1]$ and the sum is in $[1, V]$ — its log is perfectly safe; the entire instability lived in exponentiating and then taking log of a number that had already underflowed (float64 underflows below $e^{-745}$; a well-trained LM easily assigns $e^{-800}$ to garbage tokens). This is why every framework fuses the two (log_softmax, cross_entropy on logits) and why passing probabilities into a logits-expecting loss is its own classic bug (#31). The gradient also becomes the famously clean $p - y$ only in the fused form — one more reason the two-step version has no redeeming qualities.
9gradientsHand-written backprop fails the gradient check

Interviewer: "Two-layer MLP with hand-derived gradients. Loss decreases, then stalls at a mediocre level. Here's the finite-difference check output — read it and localize the bug from the numbers alone."

Gradient check: relative error ‖g_analytic − g_numeric‖ / ‖g_analytic + g_numeric‖ per parameter:
W2: 3.1e-9 ✓    b2: 1.8e-9 ✓    W1: 4.7e-1 ✗    b1: 2.2e-9 ✓
def backward(X, y, cache):
    h, probs, W2 = cache                 # h: (B, H) post-ReLU, probs: (B, C)
    dz2 = (probs - y) / len(X)           # (B, C) — CE+softmax gradient: correct
    dW2 = h.T @ dz2                      # (H, C) — correct
    db2 = dz2.sum(axis=0)
    dh = dz2 @ W2.T                      # (B, H) — correct
    dz1 = dh * (h > 0).mean()            # scalar "fraction alive" — not the per-element mask!
    dW1 = X.T @ dz1
    db1 = dz1.sum(axis=0)
    return dW1, db1, dW2, db2
Bug · fix · theory
What to look for
  • Read the check like a bisector: W2/b2/b1 pass, W1 fails ⇒ the error enters strictly between b1's gradient and W1's gradient — i.e., in dz1 (shared by both) is wrong in a way that cancels in a sum but not in a matmul, or in the dW1 line itself. A scalar mis-scaling of dz1 survives sum(axis=0)… no — it scales b1 too, so b1 passing means the corruption is per-element but averages out along the batch: exactly what .mean() of the mask does.
  • ReLU's derivative is the elementwise indicator (h > 0) — same shape as h, gating each unit. Any reduction of it (mean, sum) is a red flag.
  • Gradient-check hygiene worth saying: check with float64, $\epsilon = 10^{-5}$, on a tiny net; relative error < 1e-6 pass, > 1e-2 definite bug; check per parameter tensor to localize, not one global number.
    dz1 = dh * (h > 0)                   # elementwise mask, shape (B, H)
    dW1 = X.T @ dz1
    db1 = dz1.sum(axis=0)
Background. Backprop is the chain rule with each local Jacobian applied in sequence; ReLU's Jacobian is diagonal with entries $\mathbb{1}[h>0]$, so its vector-Jacobian product is an elementwise mask — replacing it with its average rescales every unit's gradient identically, which points $dW_1$ in a systematically wrong direction (loss still falls early because the direction correlates with the truth, then stalls: the classic "trains a bit, plateaus low" signature of a wrong but correlated gradient). The finite-difference check $\frac{L(\theta+\epsilon)-L(\theta-\epsilon)}{2\epsilon}$ is $O(\epsilon^2)$ accurate and is the only tool that proves a gradient wrong rather than suggesting it; per-tensor checking turns it into a bisection over the backward pass. Interviewers love this session because it tests whether you treat gradients as checkable artifacts or as faith.
11normalization"Here is LayerNorm — debug it" (batch-size-dependent outputs)

Interviewer: "Our transformer gives different outputs for the same input depending on what else is in the batch — and at serving time with batch size 1 it emits garbage. We traced it into this LayerNorm. Debug it."

def layer_norm(x, gamma, beta, eps=1e-5):    # x: (B, d)
    mu  = x.mean(axis=0, keepdims=True)      # axis=0: statistics ACROSS THE BATCH
    var = x.var(axis=0, keepdims=True)
    return gamma * (x - mu) / np.sqrt(var + eps) + beta
Bug · fix · theory
What to look for
  • "Same input, different output depending on the batch" is the definition of a batch-coupled operation. LayerNorm must be a per-example function; statistics over axis=0 make it accidental BatchNorm (without the running stats that make BatchNorm survivable at eval).
  • The batch-1 giveaway: with B=1, mean over axis 0 is the input itself, so $x-\mu \equiv 0$ — output is exactly $\beta$ everywhere. "Constant output at batch 1" pins this bug in one observation.
  • Axis reflex for normalization layers: LN/RMSNorm reduce over the last (feature) axis; BN reduces over batch (+spatial). When reading any norm, ask "which axis?" before anything else.
def layer_norm(x, gamma, beta, eps=1e-5):    # works for (B, d) and (B, T, d)
    mu  = x.mean(axis=-1, keepdims=True)     # per example (per token), over features
    var = x.var(axis=-1, keepdims=True)
    return gamma * (x - mu) / np.sqrt(var + eps) + beta
Background. LayerNorm computes $\hat x = (x - \mu)/\sigma \odot \gamma + \beta$ with $\mu,\sigma$ over the $d$ features of one token — deterministic, identical at train and eval, valid at batch 1, which is exactly why transformers (autoregressive, variable-length, micro-batched) use it instead of BatchNorm. Writing it with axis=-1 rather than axis=1 is not pedantry: it keeps the function correct when a sequence dimension appears, i.e. $(B,d)\to(B,T,d)$. RMSNorm drops $\mu$ and $\beta$ ($x/\mathrm{RMS}(x)\odot\gamma$) at equal quality and less compute — the Llama-family default — and the same wrong-axis bug in RMSNorm produces the same batch-coupling symptom. The interview meta-skill: normalization bugs rarely crash; they show up as behavioral anomalies (batch dependence, train/serve mismatch), so you localize them with invariance tests, not stack traces.
19attentionEvery position gets the same attention output

Interviewer: "Debugging a from-scratch transformer: the attention output rows are nearly identical for every query position, and downstream the model barely beats bigrams. Here's the attention. Tell me the invariant you'd check first."

def attention(Q, K, V):                       # Q,K,V: (T, d)
    S = Q @ K.T / np.sqrt(K.shape[-1])        # (T, T): S[i, j] = query i · key j
    A = softmax(S, axis=0)                    # axis=0 normalizes each COLUMN (over queries)
    return A @ V
Bug · fix · theory
What to look for
  • The invariant: each query's row of attention weights must sum to 1. A.sum(axis=-1) all-ones — assert it in any attention you ever write. Column-normalized attention distributes each key's influence over queries; the semantics is backwards even though every shape is identical.
  • Why outputs collapse to near-identical rows: with column softmax, each output row mixes values with weights that no longer depend (correctly) on that query; in practice rows become near-uniform mixtures — "all positions look the same" is wrong-axis softmax until proven otherwise.
  • Convention check to say out loud: rows = queries, columns = keys, softmax over keys = axis=-1. In S[i,j], i indexes the token doing the looking.
def attention(Q, K, V):
    S = Q @ K.T / np.sqrt(K.shape[-1])
    A = softmax(S, axis=-1)                   # each query's distribution over KEYS
    assert np.allclose(A.sum(axis=-1), 1.0)
    return A @ V
Background. Attention computes, per query, a convex combination of value vectors: $\mathrm{out}_i = \sum_j A_{ij} v_j$ with $\sum_j A_{ij}=1$ — the row-stochastic structure is the mechanism, and the wrong axis silently replaces "where should token $i$ look?" with "which tokens look at $j$?" (column-stochastic), destroying the convex-combination semantics while keeping every shape legal, which is why this bug survives shape-based review. It generalizes: softmax axis bugs in CE (#6), in mixture-of-experts routing, in contrastive losses (InfoNCE has both an image→text and text→image axis, and using one twice is a real CLIP-reimplementation bug). Whenever a softmax appears, the first question is "a distribution over what?" — then assert that axis sums to 1.
20attentionCausal LM: validation loss is impossibly good

Interviewer: "New decoder-only LM: train loss 1.1, val loss 1.0 after an hour — a 7B-level number from a 50M model. Generations are garbage though. The team is celebrating; you suspect the mask. Prove it and fix it."

def attention(Q, K, V, causal=True):
    T = Q.shape[0]
    S = Q @ K.T / np.sqrt(K.shape[-1])
    A = softmax(S, axis=-1)                   # softmax FIRST…
    if causal:
        A = A * np.tril(np.ones((T, T)))      # …then zero the future weights
    return A @ V
Bug · fix · theory
What to look for
  • "Too good to be true" loss in an autoregressive model = information leaking from the future. Masking after softmax breaks row normalization (rows now sum to < 1) — worse, the pre-softmax normalizer $\sum_j e^{S_{ij}}$ already included future keys, so each kept weight's value depends on future content. The target leaks through the denominator.
  • The causality unit test to name: change tokens at positions > t, assert outputs at ≤ t are bit-identical. It fails here — that's your proof, mechanical and irrefutable.
  • Also flag: zeroed rows renormalized after the fact (A /= A.sum()) still leak via the denominator gradient. The only correct place for a mask is on the scores, as −inf, before softmax.
def attention(Q, K, V, causal=True):
    T = Q.shape[0]
    S = Q @ K.T / np.sqrt(K.shape[-1])
    if causal:
        mask = np.tril(np.ones((T, T), dtype=bool))
        S = np.where(mask, S, -np.inf)        # -inf BEFORE softmax: exp→0, rows renormalize
    A = softmax(S, axis=-1)
    return A @ V
Background. With $-\infty$ on masked scores, $e^{-\infty}=0$ and the softmax renormalizes over exactly the allowed prefix — the distribution over visible keys is mathematically identical to attention computed on the prefix alone, which is the property autoregressive factorization $p(x)=\prod_t p(x_t|x_{<t})$ requires. Any post-softmax intervention fails because the partition function is a global coupling: every weight (and its gradient) is a function of all logits, including masked ones. The symptom pattern — great teacher-forced loss, garbage free-running generations — is the universal signature of train-time leakage (mask bugs, un-shifted labels #33, targets in input features), because teacher forcing hands the model the leaked answer while generation must do without it. "Suspiciously low loss is a bug until proven otherwise" is a genuine frontier-lab reflex; several published incident writeups amount to exactly this session.
22attentionNaN only for short sequences in a padded batch

Interviewer: "Batched training with padding + causal masking. Everything is fine until a batch contains one very short sequence — then the whole batch NaNs. Longer sequences never trigger it. Here's the masking code; the length-dependence is your clue."

def masked_attention(Q, K, V, pad_mask):       # pad_mask: (T,) True = real token
    T = Q.shape[0]
    S = Q @ K.T / np.sqrt(K.shape[-1])
    allowed = np.tril(np.ones((T, T), dtype=bool)) & pad_mask[None, :]
    S = np.where(allowed, S, -np.inf)          # a PAD row allows nothing → all -inf row
    A = softmax(S, axis=-1)                    # softmax of all--inf: 0/0 = NaN
    return A @ V
Bug · fix · theory
What to look for
  • "NaN only when a sequence is short" ⇒ some row of the score matrix got fully masked. A pad query position attends to… only pad keys before it — every entry $-\infty$. Then softmax computes $e^{-\infty-(-\infty)}$… the row max is $-\infty$, subtraction gives NaN, and normalization is $0/0$. One poisoned row NaNs the matmul, the loss, and (next step) the weights.
  • Rule: whenever you build masks, ask "can a row end up with zero allowed entries?" Combining masks (causal ∧ padding ∧ sliding-window) multiplies the ways it can happen — the intersection is the danger, and short sequences make it likely.
  • Both standard fixes are acceptable; say why yours works: (a) make every row attend to at least itself; (b) let the NaN rows happen, then zero them — pad positions are excluded from the loss anyway, but zeroing must occur before the values can propagate.
T=6, left-padded (P P a b c d): causal ∧ pad-key mask leaves the two PAD query rows with zero allowed entries → all-−∞ rows → softmax 0/0 = NaN. NaN then spreads: next layer computes 0·NaN in every row. Right-padding hides the bug (pad rows still see the real prefix) — which is why it detonates only on short/left-padded sequences.
def masked_attention(Q, K, V, pad_mask):
    T = Q.shape[0]
    S = Q @ K.T / np.sqrt(K.shape[-1])
    allowed = np.tril(np.ones((T, T), dtype=bool)) & pad_mask[None, :]
    allowed |= np.eye(T, dtype=bool)           # every row may attend to itself: no empty rows
    S = np.where(allowed, S, -np.inf)
    A = softmax(S, axis=-1)
    A = np.where(pad_mask[:, None], A, 0.0)    # belt & braces: pad queries output zeros
    return A @ V
Background. Softmax over an all-$-\infty$ row is undefined (the distribution has no support), and IEEE arithmetic reports that fact as NaN via $\infty-\infty$ and $0/0$; every framework reimplementation hits this eventually, and FlashAttention/SDPA kernels special-case fully-masked rows internally for exactly this reason. The bug class — degenerate mask intersections — grows with every masking feature: padding × causal × sliding-window × cross-attention with empty context, and its frequency scales with real-data length variance, which is why it escapes toy tests (all sequences same length) and detonates in production. Defensive idioms: allow self-attention on the diagonal unconditionally, or use large-negative (−1e9) instead of true $-\infty$ so a fully-masked row degrades to uniform-over-nothing-useful rather than NaN — then rely on the loss mask to make those positions irrelevant. Always pair with a test containing a length-1 sequence in a padded batch. Why self-attention on a pad row is mathematically safe: the row softmaxes over one entry → weight 1.0 on its own value $V_{\text{pad}}$ — finite garbage in a don’t-care slot. It cannot leak: real rows carry weight exactly 0 on pad columns and $0\times\text{finite}=0$ (whereas $0\times\text{NaN}=\text{NaN}$ — the whole asymmetry of the bug); all non-attention ops are position-wise, so garbage stays in its row; the loss mask zeroes its contribution; and the backward pass follows the same masked paths, so $\partial L/\partial V_{\text{pad}} = \sum_i A_{i,\text{pad}}\,\partial L/\partial \text{out}_i = 0$ — nothing is learned from pad positions. The only requirement at a pad slot is finiteness, so self-attention, attend-to-position-0, and FlashAttention’s output-zeros convention are equally valid. Two conditions carry the safety: the loss mask must actually exist (else the model trains on PAD-garbage predictions — #34’s disease, no NaN but real damage), and no unmasked global pooling downstream (a naive .mean(axis=0) ingests pad rows; attention contains them, pooling doesn’t).

14training loopLoss drops fast, then oscillates and climbs

Interviewer: "PyTorch loop, standard model. The loss falls faster than our reference for a hundred steps, then gets noisy and drifts up. LR and data are identical to the reference. Here's the loop."

Buggy run initially beats the reference (effective LR is growing), then destabilizes — accumulated gradients act like an unbounded momentum.
for x, y in loader:
    loss = F.cross_entropy(model(x), y)
    loss.backward()
    opt.step()                       # no zero_grad: .grad ACCUMULATES across steps
Bug · fix · theory
What to look for
  • "Faster than the reference at first" is the counterintuitive tell: step $t$ applies the sum of all past gradients, so the effective step size grows ~linearly — free acceleration early, unbounded instability later. A bug that initially improves results is a bug people don't look for.
  • One-line probe: log p.grad.norm() for a fixed parameter — monotone growth across steps while the loss is roughly flat proves accumulation.
  • The audit order for any PyTorch loop, recited: zero_grad → forward → loss → backward → (clip) → step → (scheduler). Check the five are present, once each, in that order.
for x, y in loader:
    opt.zero_grad(set_to_none=True)  # set_to_none: cheaper + surfaces "no grad" bugs
    loss = F.cross_entropy(model(x), y)
    loss.backward()
    opt.step()
Background. .backward() adds into .grad by design — that's the feature that makes gradient accumulation (micro-batching to simulate large batches) a three-line pattern: call backward $k$ times on scaled losses, step and zero once. Forgetting the zero turns every step into $\theta \leftarrow \theta - \eta\sum_{s\le t} g_s$, an integral controller with no damping. set_to_none=True (the modern default) frees memory and makes a parameter that never received gradient show up as None instead of a silent zero — converting a silent bug (#40's unregistered params) into a loud one. The general lesson: know which framework operations are stateful (grads, RNG, BN running stats, optimizer moments, scheduler counters) — state that outlives an iteration is where loop bugs live.

24RL"Here is the reward curve — it goes DOWN. Why?"

def policy_update(logps, rewards, params, lr):
    # REINFORCE: ∇J = E[R · ∇log π(a|s)] — "so the loss is logp times reward"
    loss = (logps * rewards).mean()           # this is +J, the thing to MAXIMIZE
    grads = compute_grads(loss, params)
    params -= lr * grads                      # gradient DESCENT on +J = minimizing reward
    return params
Bug · fix · theory
What to look for
  • Smooth monotone decline ≠ "not learning." Not-learning looks like a flat noisy line; a consistent decline is successful optimization of the negated objective — a sign error in exactly one place. (Two sign errors put you back to correct; it happens.)
  • The convention trap: papers state objectives to maximize; optimizers minimize. Every RL implementation must negate once, deliberately: loss = −E[logπ·R]. Audit where the negation lives, and that it lives in exactly one place.
  • Say the 30-second unit test: a bandit with two actions, rewards 1 and 0 — after a few updates the good action's probability must increase. It's the cheapest directional test in RL, and it catches sign errors in REINFORCE, PPO, DPO alike.
def policy_update(logps, rewards, params, lr):
    baseline = rewards.mean()                 # variance reduction (unbiased: E[∇logπ]=0)
    loss = -(logps * (rewards - baseline)).mean()   # MINIMIZE the NEGATIVE objective
    grads = compute_grads(loss, params)
    params -= lr * grads
    return params
Background. The policy-gradient theorem gives $\nabla_\theta J = \mathbb{E}[(R-b)\,\nabla_\theta\log\pi_\theta(a|s)]$ — an ascent direction; any baseline $b$ independent of the action leaves it unbiased because $\mathbb{E}[\nabla\log\pi] = 0$, while dramatically cutting variance (that's the mean-baseline line in the fix, the same idea GRPO scales to groups). Sign discipline matters more in RL than anywhere else because the pipeline has several sign-sensitive quantities stacked: reward vs cost, advantage vs regret, KL penalty vs KL bonus (#50), logp vs negative-logp — and a single flip anywhere produces the same clean "learns the wrong thing" curve. Frontier habit: every RL codebase carries direction tests (reward-up-on-bandit, KL-positive, clip-fraction-nonzero) as CI, precisely because sign bugs are silent, smooth, and catastrophic.

13normalizationBatchNorm: val metrics depend on eval batch size

Interviewer: "A CNN's validation accuracy changes when we change the eval dataloader's batch size — 88% at batch 256, 71% at batch 8, and NaN at batch 1. Training is untouched. What single concept explains all three numbers?"

def batch_norm(x, gamma, beta, eps=1e-5):        # called identically at train AND eval
    mu  = x.mean(axis=0)                          # batch statistics recomputed at eval
    var = x.var(axis=0)                           # batch=1 → var=0 → division blows up
    return gamma * (x - mu) / np.sqrt(var + eps) + beta
Bug · fix · theory
What to look for
  • Eval metrics that depend on eval batch size can only come from an op that couples examples — and BatchNorm is the only standard one. Large eval batches ≈ good statistics (88%), small batches ≈ noisy statistics (71%), batch 1 ≈ degenerate ($\mu = x$, $\mathrm{var}=0$, output $=\beta$, or NaN upstream).
  • The missing machinery: running statistics accumulated during training (EMA of $\mu,\sigma^2$) and used instead of batch stats at eval. If a BatchNorm implementation has no training flag, it's wrong by construction.
  • In frameworks this exact symptom usually means model.eval() was never called — same disease, one line.
class BatchNorm:
    def __init__(self, d, eps=1e-5, momentum=0.1):
        self.gamma, self.beta = np.ones(d), np.zeros(d)
        self.run_mu, self.run_var = np.zeros(d), np.ones(d)
        self.eps, self.m = eps, momentum
    def __call__(self, x, training):
        if training:
            mu, var = x.mean(axis=0), x.var(axis=0)
            self.run_mu  = (1-self.m)*self.run_mu  + self.m*mu     # EMA during training
            self.run_var = (1-self.m)*self.run_var + self.m*var
        else:
            mu, var = self.run_mu, self.run_var    # frozen population stats at eval
        return self.gamma * (x - mu) / np.sqrt(var + self.eps) + self.beta
Background. BatchNorm normalizes each feature using batch statistics at train time (which also injects a mild, batch-size-dependent regularization noise), but inference must be a deterministic per-example function — hence the EMA "population" statistics. Everything painful about BN follows from this coupling: small-batch training degrades (noisy stats), sync-BN is needed across data-parallel workers, and it's unusable for autoregressive decoding — the concrete reasons transformers standardized on LayerNorm (#11). A second-order interview point: train/eval BN discrepancy also appears when the data distribution shifts after training (running stats go stale), which is one of the classic silent killers in production vision systems.

What to look for

Background. With $y = x + F(x)$, the block Jacobian is $I + \partial F/\partial x$, so the end-to-end gradient $\prod_l (I + J_l)$ contains a pure-identity term: signal reaches layer 1 undamped regardless of depth. Remove the skip and the gradient is $\prod_l J_l$, whose norm scales like $\sigma^L$ — the vanishing/exploding mechanism of #10, now at the block level, which is precisely why "24 layers ≈ 2 layers": only the top few layers receive usable gradient. Sharp follow-up you may get: in post-norm ($\mathrm{LN}(x + F(x))$) the identity path runs through the LN, which partially re-attenuates gradients — the historical reason original-transformer training needed warmup so badly.
Common mis-fix — one residual is not two.
  • Tempting rewrite: y = attn(ln1(x)); y = mlp(ln2(y)); x = x + y. It looks fixed and it does train — output is x + g(x), so the Jacobian I + J_g still has an identity path and you won't see the geometric gradient decay. That's the trap: it silences #39's dramatic symptom while being a different, weaker block (converges but lands short — the #36 flavor).
  • Two things broke: (1) attention lost its own skip — a = attn(ln1(x)) reaches the output only through the MLP, never written directly to the stream; (2) the MLP reads ln2(a) (attention output) instead of ln2(x+a) (the residual stream). You serialized two sublayers into one branch mlp∘attn and halved the skips per block.
  • Rule: each sublayer gets its own x +. The legit compression is parallel, not serial — GPT-J/PaLM do x = x + attn(ln(x)) + mlp(ln(x)) (both branches read x, both added, often one shared LN). Serial x + mlp(attn(x)) is not a standard block.

def patchify(img, P=4):

    x = img.reshape(H // P, P, W // P, P, C)      # split BOTH spatial axes in place

What to look for

    A = X.T @ X + lam * np.eye(d)        # ridge: A ≻ 0, always invertible
    return np.linalg.solve(A, X.T @ y)   # solve, never inv — better speed & stability
# or: np.linalg.lstsq(X, y, rcond=None) — SVD-based, handles rank deficiency directly
Background. $X^\top X$ is invertible iff $X$ has full column rank; one-hot encodings with an intercept (the "dummy-variable trap"), duplicated features, and $d > n$ all break it.
